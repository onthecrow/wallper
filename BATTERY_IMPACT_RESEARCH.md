# Расход батареи Wallper: можно ли посчитать без root и особых разрешений

> **Коротко.**
> - **Точно как в системном экране «Батарея» — нельзя.** Попроцессная статистика (`BatteryStats` / `BatteryUsageStats`) закрыта разрешением `BATTERY_STATS`. Магазинное приложение его не получит, только пользователь через adb.
> - **Честную оценку — можно**, и без единого разрешения. Общий расход телефона даёт `BatteryManager` (счётчик заряда). Свою долю считаем сами: замеряем, насколько вырастает ток устройства, когда обои анимируются, и умножаем на время, пока они видны.
> - **Итоговая цифра:** «Wallper ≈ X% расхода батареи с последней зарядки» и «≈ Y мА / Z% батареи в час, пока обои на экране». Погрешность — примерно ±20–40% после калибровки и до ±2 раз без неё.
> - **Наша цифра будет выше системной, и это правильно.** Системный экран почти не приписывает живым обоям GPU и композицию кадров, то есть как раз основную их стоимость.
> - **На Android 15+ с ODPM** (Pixel 6 и новее) есть `PowerMonitor` API без разрешений: реальная энергия GPU и CPU, но по всему устройству, с кешем 30 с и шумом. Это хороший уточнитель, но не основа.

## 1. Что именно показывать

> **Коротко.** «% относительно остальных приложений и системы» — это доля Wallper во всём расходе батареи за период. Знаменатель мы получаем точно, числитель только оцениваем.

```
доля Wallper = Q_wallper / Q_total

Q_total   = сколько мА·ч устройство потратило за период (на батарее)           ← BatteryManager, точно
Q_wallper = Σ по режимам (ток, который добавляют обои в режиме m) × (время в режиме m)   ← наша оценка
```

Что показывать в настройках:
- **основное:** «≈ 4% расхода батареи с последней зарядки (≈ 120 мА·ч)»;
- **понятное в моменте:** «пока обои на экране: ≈ 45 мА, это ≈ 1% батареи в час»;
- **ссылку** «Системная статистика» на экран батареи (`Intent.ACTION_POWER_USAGE_SUMMARY`), с пометкой, почему цифры отличаются (§4).

Режимы m — те, что уже есть в движке: 60 fps, 30 fps, 24/15 fps, неподвижный кадр, обои скрыты. Для видео: воспроизведение, пауза, скрыто.

## 2. Что закрыто и почему

> **Коротко.** Всё, что даёт расход других приложений, требует системных разрешений или закрыто SELinux. Обходы через скрытые API ненадёжны и рискованны для стора.

| Источник | Что дал бы | Почему нельзя |
|---|---|---|
| `BatteryStatsManager` / `BatteryUsageStats`, `dumpsys batterystats` | ровно то, что показывает системный экран: мА·ч и % по каждому UID | `BATTERY_STATS` выдаётся только системным приложениям; `dumpsys` требует `DUMP`. Обычному приложению из стора их не получить. Пользователь может выдать `BATTERY_STATS` вручную через `adb shell pm grant` (так делает BetterBatteryStats), но и тогда сам `BatteryUsageStats` — системный API, вне SDK |
| `SystemHealthManager.takeUidSnapshot(чужой uid)` | статистика по другим приложениям | «An application must hold the BATTERY_STATS permission in order to retrieve any HealthStats other than its own» |
| `UidHealthStats.MEASUREMENT_CPU_POWER_MAMS` (свой uid) | модельная энергия нашего CPU | помечено deprecated: «vendor-dependent and not reliable» |
| `/proc/stat`, чужие `/proc/<pid>` | общая загрузка CPU | закрыто SELinux для `untrusted_app` с Android 8 (neverallow на `proc_stat`) |
| `PowerProfile` (`power_profile.xml`, коэффициенты мА по компонентам) | готовая модель мощности устройства | скрытый API `com.android.internal`, блокируется ограничениями non-SDK |
| `PACKAGE_USAGE_STATS` | время использования приложений | энергии не даёт, а пользователь должен выдать доступ вручную в настройках |

**Вывод:** долю каждого чужого приложения мы не узнаем. Но для «доли Wallper» достаточно знать общий расход устройства, а он доступен (§3).

## 3. Что доступно без разрешений

> **Коротко.** Общий расход устройства, свой CPU, свой GPU и (на Android 15+ с ODPM) энергия подсистем устройства. Этого хватает на оценку.

| Источник | Что даёт | Ограничения |
|---|---|---|
| `BatteryManager.BATTERY_PROPERTY_CHARGE_COUNTER` | остаток заряда в мкА·ч → `Q_total` за период | на части устройств не поддерживается (`Long.MIN_VALUE`/0) или обновляется ступенями |
| `BATTERY_PROPERTY_CURRENT_NOW` / `CURRENT_AVERAGE` | ток всего устройства (мкА; минус = разряд) | см. §7: единицы, знак и частота обновления на разных устройствах разные; `CURRENT_AVERAGE` часто не поддержан |
| `ACTION_BATTERY_CHANGED` (sticky) | уровень %, напряжение, подключена ли зарядка | — |
| ёмкость батареи | `CHARGE_COUNTER / (уровень / 100)` | только если есть `CHARGE_COUNTER` |
| `SystemHealthManager.takeMyUidSnapshot()` | свой CPU user/system, время сенсоров, состояния процесса | своё приложение без разрешений; энергии нет |
| `Process.getElapsedCpuTime()` | CPU-время процесса | только своё |
| `EXT_disjoint_timer_query` (уже есть в рендерере) | GPU-время каждого кадра чёрной дыры | не везде (много Mali без него); видео-путь не покрывает |
| `SystemHealthManager.getSupportedPowerMonitors()` / `getPowerMonitorReadings()` (API 35) | энергия ODPM-рельс и «потребителей» (`GPU`, `CPU`, `DISPLAY`, …) в мкВт·с | **по всему устройству**, не по UID; пустой список без ODPM (кроме Pixel 6+ встречается редко); показания обновляются раз в 30 с (`MAX_POWER_MONITOR_AGE_MILLIS`); добавляется случайный шум до 10 Дж на показание |
| `Intent.ACTION_POWER_USAGE_SUMMARY` | открыть системный экран батареи | только переход, данных не даёт |

Проверка в исходниках `PowerStatsService`: на методах power monitor нет проверки `BATTERY_STATS` и фильтрации по вызывающему. Для обычного приложения отличаются только кеш на 30 с и шум.

## 4. Почему системный экран недооценивает живые обои

> **Коротко.** Система приписывает приложению CPU, wakelock'и, сенсоры и радио. Энергия GPU и SurfaceFlinger'а, которую тратят обои, в основном уходит в «Экран» и «Система». Поэтому в Settings Wallper будет выглядеть дешевле, чем есть.

- **Что попадает в строку Wallper.** Только CPU нашего процесса (а мы стараемся его не грузить), сенсоры (гироскоп) и wakelock'и.
- **Что попадает в «Экран» / «Система» / «Android OS».**
  - Работа GPU (на большинстве устройств), композиция кадров SurfaceFlinger'ом, аппаратный видеодекодер.
  - На Pixel с ODPM энергия GPU распределяется модельно и тоже не обязательно попадает к нам.
- **OLED.** Тёмная чёрная дыра заметно дешевле для экрана, чем яркая статичная картинка: на OLED энергия пропорциональна яркости пикселей. Это плюс обоев, но его не видно ни в системной статистике, ни в нашей оценке «прироста от анимации». Его можно упомянуть текстом.

**Что из этого следует для UI:** наша цифра — «сколько стоит анимация обоев целиком». Системная — «сколько стоит процесс Wallper». Нужна короткая подпись, почему они разные, иначе пользователь решит, что одна из них неверна.

## 5. Варианты оценки

> **Коротко.** Три способа посчитать `Q_wallper`. A — модель по нашим счётчикам, работает везде, но грубо. B — калибровка по току устройства: точнее всего, но обоям приходится ненадолго замирать. C — ODPM на Android 15+: точно по GPU, но мало устройств.

### A. Модель по своим счётчикам (везде, без замеров тока)

```
I_wallper ≈ k_gpu · (GPU-мс в секунду) + k_frame · fps + k_cpu · (CPU-мс в секунду) + I_gyro · [гироскоп включён]
```
- GPU-мс берём из timer query (уже есть), CPU — из `takeMyUidSnapshot()`, fps — из пейсера.
- Коэффициенты `k_*` — типовые для класса SoC. Мы меряем их сами в лаборатории (Perfetto power rails на Pixel, `dumpsys batterystats` на паре устройств) и вшиваем таблицу.
- **Погрешность:** до 2 раз. Мощность GPU на одинаковой нагрузке отличается у разных SoC в разы. Без timer query (часть Mali) остаётся только fps.
- **Для видео:** GPU-времени нет, есть только «видео воспроизводится, разрешение, fps» × типовой ток декодера.

### B. Калибровка по току устройства (везде, где есть `CURRENT_NOW`)

Идея — A/B-замер прироста тока, который дают обои:

```
калибровка (≈ 40 с, обои видны, телефон не трогают, на батарее):
  6 раз:  [5 с анимации] → [5 с неподвижного кадра]
  в каждом блоке пропускаем первые 1.5 с (инерция усреднения в контроллере батареи)
  I_mode = медиана(ток в блоке «анимация») − медиана(ток в блоке «стоп»)
```
- **Что измеряется.** Ровно то, что добавляет анимация: GPU, CPU, композиция, память, для видео — декодер. Экран и остальная система вычитаются сами собой.
- **Погрешность:** обычно ±20–40%. Шум дают фоновая активность, радио и шаг обновления тока; уменьшаем повторами и медианой. Если разброс большой, калибровку повторяем или сообщаем «не удалось измерить».
- **UX.** Делать её незаметно в фоне нельзя: обои будут вдруг замирать на 5 с. Поэтому калибровка запускается по кнопке в настройках: «Вернитесь на главный экран и не трогайте телефон 40 секунд». Результат сохраняется для устройства и режима.
- **Режимы.** Меряем режим покоя (30 fps), остальные масштабируем по fps. Отдельно можно мерить 60 fps (с эмуляцией активности) и видео (пауза против воспроизведения).

### C. ODPM на Android 15+ (`PowerMonitor`)

- Энергия потребителей `GPU` и `CPU` между двумя показаниями, пока обои видимы и главный экран неподвижен, почти целиком принадлежит нам. Лаунчер на неподвижном экране GPU почти не нагружает.
- **Погрешность:** хорошая на длинных интервалах. Шум до 10 Дж против ~500 Дж GPU за 30 минут — около 2%. Короткие замеры невозможны из-за кеша на 30 с.
- **Ограничения.** Названия рельс и потребителей зависят от устройства. Устройств с ODPM немного (в основном Pixel 6+). Есть смещение вверх: всё, что ещё рисуется на главном экране, тоже попадёт к нам.

| | A. Модель | B. Калибровка | C. ODPM |
|---|---|---|---|
| Устройства | все | почти все | Android 15+ с ODPM |
| Погрешность | до ×2 | ±20–40% | ±10–20% (GPU+CPU), без композиции |
| Нужен пользователь | нет | один раз, 40 с | нет |
| Видео-путь | грубо | да | частично (если есть рельса декодера) |
| Сложность | низкая | средняя | средняя |

## 6. Рекомендация

> **Коротко.** Делаем A как основу, B как одноразовую калибровку по кнопке, а C — как автоматическое уточнение там, где оно есть. Показываем «≈», диапазон и подпись про системный экран.

1. **Всегда (A).** Движок копит время по режимам и счётчики (GPU-мс, кадры, CPU-мс, время гироскопа) в device-protected хранилище: сервис работает в direct boot. Оценка доступна сразу, с пометкой «примерно».
2. **Калибровка (B).** Кнопка «Уточнить на этом телефоне» на экране настроек. Измеренные `I_mode` заменяют коэффициенты модели для этого устройства, и точность в UI меняется на «±30%».
3. **Уточнение (C).** На Android 15+, если есть потребитель `GPU`, движок раз в N минут видимости снимает показания и сглаженно подправляет `k_gpu`.
4. **Знаменатель.** Сумма уменьшений `CHARGE_COUNTER`, пока устройство на батарее. Сбрасывается при полной зарядке (уровень 100% и подключено), как в системе. Без `CHARGE_COUNTER` — падение уровня в % × ёмкость; если и ёмкость неизвестна, показываем только «% батареи в час».
5. **UI:**
   - «Wallper ≈ 4% расхода с последней зарядки»;
   - «Пока обои на экране: ≈ 45 мА (≈ 1%/ч)»;
   - кнопка «Системная статистика»;
   - сноска: «Система учитывает только процесс Wallper, без работы видеокарты и экрана, поэтому там цифра ниже».

**Почему не только B.** Калибровка требует действия пользователя, а большинство его не сделает. Цифра нужна сразу.

**Почему не только A.** Разброс коэффициентов между SoC слишком велик, чтобы показывать проценты без оговорок.

## 7. Подводные камни

> **Коротко.** Ток устройства — шумный и непереносимый сигнал. Нужно нормализовать единицы и знак, отбрасывать зарядку и переходные участки и брать медиану.

- **Единицы `CURRENT_NOW`.** По документации — мкА. На части устройств (по опыту сообщества, особенно старые Samsung) приходят мА. Определяем по порядку величины: |значение| < 10 000 при работающем экране — это мА.
- **Знак.** По документации минус означает разряд. Встречаются устройства с обратным знаком. Используем модуль и состояние «на батарее» из `ACTION_BATTERY_CHANGED`.
- **Частота и усреднение.** Значение может обновляться раз в 1–10 с и уже быть усреднённым контроллером. Отсюда блоки по 5 с с отбрасыванием начала. Если за блок значение ни разу не изменилось, замер отбрасываем.
- **Не поддерживается.** `Long.MIN_VALUE` или 0 → вариант B недоступен, остаются A и C.
- **Зарядка.** Во время зарядки ток не говорит о расходе. Калибровку не запускаем, накопление знаменателя приостанавливаем.
- **Перегрев и энергосбережение.** В этих режимах движок сам снижает fps или замирает. Калибровку не начинаем, время учитываем по фактическому режиму.
- **Несколько Engine.** Превью в пикере и основной считаются раздельно; превью стоит исключить, оно живёт секунды.
- **Видео-путь.** Отдельный набор режимов (декодер + GL или прямой вывод). Калибровка: пауза против воспроизведения.
- **Шум ODPM.** До 10 Дж на показание — брать только интервалы ≥ 10 минут видимости.
- **Хранение.** Счётчики пишутся редко (раз в минуту и при скрытии обоев), в device-protected SharedPreferences. Сбрасываются при полной зарядке.

## 8. План реализации

> **Коротко.** Около 3–4 дней: счётчики в движке, накопитель расхода, модель, калибровка и экран. ODPM — ещё день, по желанию.

1. **`core:engine:impl`:**
   - `EnergyLedger` — время по режимам, GPU-мс, кадры, CPU-мс, гироскоп;
   - запись в device-protected хранилище;
   - сброс при полной зарядке.
2. **`core:engine:impl`:** `BatteryMeter` — `CHARGE_COUNTER` / `CURRENT_NOW` с нормализацией единиц и знака, `ACTION_BATTERY_CHANGED`.
3. **Чистая логика на JVM, с тестами:**
   - `EnergyModel` — коэффициенты по классу SoC и формула A;
   - `CalibrationRun` — блоки, отбрасывание переходов, медианы, оценка разброса.
4. **Калибровка:**
   - команда от экрана настроек к движку (через порт в `core:engine:api`);
   - движок чередует анимацию и неподвижный кадр и публикует результат.
5. **Экран:** блок «Батарея» в настройках (чёрная дыра и общий для видео), кнопки калибровки и системной статистики.
6. **По желанию — ODPM (API 35):** `PowerMonitorSampler` для поправки `k_gpu`.
7. **Лабораторная таблица коэффициентов:**
   - Perfetto power rails на Pixel, `dumpsys batterystats` на 2–3 устройствах других SoC;
   - это делаем мы, а не пользователь.

**Решения, которые нужны от тебя:**
- показывать ли цифру сразу, по модели (рекомендую да, с «≈» и пометкой точности);
- устраивает ли калибровка по кнопке с замиранием обоев на 5-секундные блоки.

## 9. Источники

- [SystemHealthManager.java (AOSP)](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/os/health/SystemHealthManager.java): `takeUidSnapshot` требует `BATTERY_STATS` для чужих UID; `getSupportedPowerMonitors` / `getPowerMonitorReadings`.
- [PowerMonitor.java (AOSP)](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/os/PowerMonitor.java): типы MEASUREMENT (ODPM-рельса) и CONSUMER (подсистема, например GPU).
- [PowerStatsService.java (AOSP)](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/services/core/java/com/android/server/powerstats/PowerStatsService.java): нет проверки разрешений на power monitors, кеш 30 с, шум до 10 Дж.
- [SystemHealthManager — API diff 35](https://developer.android.com/sdk/api_diff/35/changes/android.os.health.SystemHealthManager): методы power monitor добавлены в API 35.
- [UidHealthStats.java (AOSP)](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/os/health/UidHealthStats.java): `MEASUREMENT_CPU_POWER_MAMS` deprecated как ненадёжный.
- [BatteryManager](https://developer.android.com/reference/android/os/BatteryManager): `CURRENT_NOW` в мкА, знак, `CURRENT_AVERAGE` зависит от контроллера батареи.
- [AOSP sepolicy: neverallow proc_stat для untrusted_app](https://gitlab.cs.fau.de/Matombo/AndroidSystemSEPolicy/-/commit/3079d01ad8b02a6bed7c916c7bb6090eca18f8d7.patch): `/proc/stat` закрыт для приложений.
- [BetterBatteryStats: выдача BATTERY_STATS через adb](https://www.xda-developers.com/betterbatterystats-2-3-android-oreo-support-unrooted/): пример ручной выдачи разрешения пользователем.
