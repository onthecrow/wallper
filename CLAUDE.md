# Wallper

Android live wallpaper app: the user crops a video, Wallper plays it as the live wallpaper.
Design docs: [WALLPER_PLAYER_DESIGN.md](WALLPER_PLAYER_DESIGN.md) (video playback and stalls), [BLACKHOLE_PLAN.md](BLACKHOLE_PLAN.md) (the black hole). Open review findings and the release plan: [CODE_REVIEW.md](CODE_REVIEW.md).

## Build and test

```bash
./gradlew assembleDebug unitTest lintDebug
```

- `unitTest` (from the convention plugins) runs `test` in plain Kotlin modules and `testDebugUnitTest` in Android ones; plain `testDebugUnitTest` skips the JVM modules.
- Lint warnings fail the build. Older ones are kept in each module's `lint-baseline.xml`; don't add to it, fix new warnings.
- CI (`.github/workflows/ci.yml`) runs `unitTest lintDebug assembleRelease validateBlackHoleShaders` on every pull request.
- `app/google-services.json` isn't in git. Without it the build only warns: the release build has no Firebase app and uploads no R8 mapping (as on CI). With it, a release build uploads its mapping to Crashlytics.
- Release signing reads the Play upload key from `~/.gradle/gradle.properties`, the environment or `singning/signing.properties` beside the key (git ignores the folder): `WALLPER_UPLOAD_STORE_FILE` (relative to the project root), `WALLPER_UPLOAD_STORE_PASSWORD`, `WALLPER_UPLOAD_KEY_ALIAS`, `WALLPER_UPLOAD_KEY_PASSWORD`. Without them the release build is unsigned; never put them in the repository. Publish with `./gradlew bundleRelease`.

## Modules

- `:app`: Application, MainActivity, `@StartDestination`. No feature code.
- `:core:*`: `model` (pure Kotlin), `diagnostics` (pure Kotlin), `coroutines`, `mvi`, `navigation:api|impl`, `designsystem`, `resources`, `storage`, `haptics` (`Haptics`, ticks on the system vibrator, no view needed), `gl`, `player`, `engine:api|impl` (the WallpaperService). Core knows no built-in wallpaper by name.
- `:feature:<name>:{logic-api, logic-impl, ui-api, ui-impl}`: `wallpapers` (main screen, owns the wallpaper domain and Room, and the groups: series), `editor` (add screen, media prep, Transformer export), `blackhole` (the built-in black hole: physics and the screens' ports in `logic-api`, the GLES 3.0 renderer, its engine and the settings store in `logic-impl`, settings and debug screens in `ui-impl`), `settings` (the app's settings: `AppSettings` in `logic-api`, its store and the report in `logic-impl`, the settings and storage screens in `ui-impl`).

## Dependency rules (enforced by `build-logic/.../ModuleBoundaries.kt`)

- A feature sees another feature only through `ui-api` (navigation) and `logic-api` (domain). Only `:app` depends on `-impl`.
- Inside a feature, logic never depends on UI: `ui-impl` → `ui-api`, `logic-api`; `logic-impl` → `logic-api`. `logic-api` is plain Kotlin (`wallper.jvm.library`).
- `core` never depends on `feature`. When core needs feature data, core declares a port (`ActiveWallpaperSource`) and the feature implements it.
- `core:model`, `coroutines`, `storage`, `gl`, `player`, `engine:*` and every feature `logic-*` stay free of Compose and `core:designsystem`.
- `core:engine:api` exposes `core:gl`: a series hands a slide the `GlHost` its renderer runs on (`SlideStart`).
- Everything in `-impl` is `internal`; Hilt modules are the only public surface.

## Invariants

- The wallpaper service is `directBootAware`: everything it reads (Room DB, media files, thumbnails) lives in device-protected storage. `Application.onCreate` and the Hilt graph must not touch credential-encrypted storage.
- The editor's scratch files (`MediaStorage.temp*`: the copy of the picked media, its thumbnail, the export) live in device-protected `files/editor`, not `cacheDir`: the system empties the cache whenever it needs space, also mid-edit. They are cleared when an edit starts (`PrepareMediaUseCase`, `PrepareSavedMediaUseCase`) and when the editor closes (`DiscardPreparedMediaUseCase`), and copied to permanent storage only once the wallpaper is saved; a failed save deletes its copies. No file outlives a wallpaper that wasn't saved.
- The user's wallpapers are of two kinds. `Wallpaper.Media` keeps the original in device-protected `filesDir`, cropped and trimmed while it plays (GL), and can be edited (`EditorDestination.Edit`): the editor opens the original where it is, and a save as «Original» only rewrites the row. `Wallpaper.ProcessedVideo` («Optimised» in the editor) keeps only the editor's export, played as is, and can only be deleted; rows from before schema v4 may still keep the original too. An edit saved as «Optimised» turns `Media` into `ProcessedVideo`: `UpdateWallpaperUseCase` deletes the files the old row had and the new one doesn't, after the update.
- The user's wallpaper may have a tint (`Tint`, `core:model`: a colour as Android packs it, which the picture is seen through like tinted glass; `wallpapers.tint`, schema v7, NULL for none, never a transparent one). It is there to make icons and text stand out, so it only ever darkens: each channel of the picture is multiplied by `1 - alpha * (1 - colour)` (`Tint.redFactor` and the others), in the picture's own gamma values. White changes nothing, a darker or more saturated colour takes more away, alpha is the strength; a colour laid over the picture instead would lighten its dark parts. `Wallpaper.Media` is drawn through it each frame (see «Stall protection», GL); the export puts it into the frames of a `ProcessedVideo` (`TintMatrix`, a Media3 `RgbMatrix` folded into the crop's shader), which plays as is and whose row keeps the tint only for its thumbnail. No thumbnail file has the tint in it, and the app's lists show the pictures without it: the list's cards, the series' pictures, pick step and member rows, the storage rows (a tint is made for icons over a whole screen; on a small picture it only makes it dark). The editor's preview multiplies its picture by `Tint.multiplierArgb` (`Modifier.wallpaperTint`, `core:designsystem`, a `Modulate` blend), and the system's colours in `WallperWallpaperService` take the tint in (a picture gets them from itself, having no thumbnail).
- A group (`Wallpaper.Group`, a series) shows other wallpapers in turn, never groups. It is a row of `wallpapers` with `slide_duration_ms` and maybe a `transition` between its slides (`TransitionEffect.key`, NULL for none) with `transition_ms` (schema v8; placeholders in the media columns, like a built-in) and its members in `wallpaper_group_items` (schema v6), whose foreign keys cascade: a deleted wallpaper leaves every group, a deleted group leaves its members, and `DeleteWallpaperUseCase` deletes a group left with fewer than `Wallpaper.Group.MIN_MEMBERS` (2): a series of one would be that wallpaper. An active one gives the screen to the member it leaves (activated as a pick), which is what it showed. The service gets `WallpaperSpec.Series`; see «Series» below.
- The main list's grid stops at its end above the «+», not under it. Its title is the brush lettering (`WallperTitle`): while Wallper is the phone's wallpaper (`LiveWallpaperController.isWallpaperSet`, checked at the start, on resume and when the system's colours change) a brush writes it as the splash's W is written, it stays 2 s, the brush takes it away from the left and writes it again; otherwise it is just there, and before that is known it isn't yet. The letters are drawn whole in a layer and kept where the brush went (`TitleBrush`: its way through them, made from their skeleton, each point with the letter's half-width there; tested on the JVM; make it again if the lettering changes). A list card (`WallpaperCard`) has no menu. The active one glows round its edge (Nimbus, `io.github.onthecrow:nimbus`, as round the connect button of OnthecrowVPN; it brings Compose 1.11 and needs API 26: older devices show no glow), in the theme's accent and its tertiary at full strength (`vivid`: the theme's tones are pastel in the dark and a glow in them is white); the glow comes and goes with the activity, follows the card's shape (`CardShape`, also the card's) and fills it under the card, which is drawn over its neighbours (`zIndex`), as the glow reaches them. The glow never goes out while the card is active. The list goes on under the app bar and the system's navigation. The bar is clear: at the list's top the glow reaches over it. Scrolled (`LazyGridState.canScrollBackward`), what goes under it is blurred and dimmed by the background's colour, faded in, both the most at the top and none at the bar's bottom edge (Haze: `hazeSource` on the list, `hazeEffect` with a progressive blur and a gradient tint on the bar; blur from Android 12, a scrim before it; `dev.chrisbanes.haze` 1.7.2, the last one on Compose 1.10, later ones bring 1.12). Edit (the editor, or a built-in's settings; none for optimised videos) and delete (not for built-ins; it asks first with `DeleteWallpaperDialog`, `core:designsystem`, shared with the storage screen) go top right, and a pill label smaller than Material's chips bottom right: «Original» (filled) / «Optimised» (outlined) for the user's media, «3D animation» (filled) for the black hole, «Series» (filled) for a group, whose picture is made of its first members' (see «Series») and whose edit opens its members. Each element shades its corner (`cornerShade`, a gradient sized by the element). A tap activates it.
- App settings (`AppSettings`, `feature:settings:logic-api`) follow the black hole's: one JSON string in device-protected SharedPreferences (`AppSettingsStore`), only what differs from the defaults, a field's name is its key. The wallpaper reads its ones in direct boot through the port `WallpaperSettingsSource` (`core:engine:api`); the app's theme (`ThemeMode`, the system colours of Material You) is applied in `MainActivity`. A new wallpaper becomes the active one unless the user turned it off (`SaveWallpaperUseCase`); hidden built-ins stay listed while one is the active wallpaper.
- A theme picked in the settings comes in a growing circle, as in NomadRates (`ThemeRevealHost`, `ThemeRevealState`, `core:designsystem`). `MainActivity` hosts the whole app in it; the settings screen calls `LocalThemeRevealState.current.reveal` with the point where the option was pressed, in screen coordinates (`ChoiceDialog` reports it: a dialog is a window of its own), and the event that stores the theme. The host keeps its last frame in a layer: the old theme is frozen into a snapshot over the app, and once the new theme has reached the host a hole in it grows from the press to the farthest corner (500 ms, `FastOutSlowInEasing`, maths in `ThemeRevealMath`, tested on the JVM). Meanwhile touches go nowhere and the system bars keep the old theme (`WallperTheme(systemBarsDarkTheme)`). A pick that doesn't turn the app dark or light (`ThemeMode.isDark`), Material You's switch, or a capture that fails switch without it. The store reads the settings before the first frame, so the app is never drawn in a guessed theme first.
- Every screen's app bar has its title centred (`CenterAlignedTopAppBar`). The settings screen follows Pixel's, with a plain bar (no large collapsing title, it only takes room): sections with accent headers, rows that toggle as a whole (`SwitchItem`, `Role.Switch`), single choices in a dialog that closes on a pick (`ChoiceDialog`), the app's version under the author's card. Storage lists the user's wallpapers by size (`ObserveWallpaperStorageUseCase`) with edit and delete as on the list's card; a video is optimised in its editor. «Send a report» writes the app's version, the device and its own log (`logcat -d`) to `cache/reports` (`CreateReportUseCase`) and shares it through the FileProvider of `feature:settings:ui-impl`.
- No cloud backup (`allowBackup="false"`, `data_extraction_rules.xml`): the videos don't fit its quota. A device-to-device transfer still moves everything.
- The privacy policy is `docs/privacy-policy.html`, served by GitHub Pages from `main`'s `/docs` (`https://onthecrow.github.io/wallper/privacy-policy.html`) and opened from the settings' Privacy section. A change to what leaves the phone (Firebase and what it collects, the switch that turns it off, the advertising ID, the report) or to what the app keeps changes the policy too, and its date.
- GL calls only from the EGL thread (`WallpaperGLThread`). Transformer only from the main looper (`TransformerVideoExporter` uses `flowOn(main)`).
- After the store release:
  - never rename `com.onthecrow.wallper.core.engine.impl.WallperWallpaperService`; the system stores it as the selected wallpaper;
  - every Room schema change needs a migration and a migration test; schemas are exported to `<module>/schemas`.

## Stall protection (see WALLPER_PLAYER_DESIGN.md)

The player side and the GL side recover independently; there is no shared abstraction between them.

- **Player (`core:player`).** `WallperPlayer` is a plain player to its consumers: `setVideoSurface`, `play`, `pause`, `setLooping`, `seekToStart`, `release`, `state`. It never exposes its ExoPlayer engines.
  - It loops by default. Without looping the clip ends on its last frame: the engine reports `isEnded`, the supervisor stops watching and the state is `Ended`, not a stall. It stays there through pauses until `seekToStart`, or until looping is back on.
  - A loop ends with the file's video track, even if the clip ends later (`loopEndUs`, tested on the JVM; `ExoEngineFactory` reads the track's end once, with `MediaExtractor`). The next loop starts when ExoPlayer's period is over, and a period lasts as long as the longest track: a sound track that outlasts the video (it is never played), or a clip saved to the end of such a file, held the last frame for the difference at every loop (150 ms where the sound was 119 ms longer).
  - A clip that starts off a key frame has a lead-in: the frames from the key frame before its start, which the decoder goes through at every loop. Media3 would start each loop of such a clip with a discontinuity (`ClippingMediaPeriod`): play the decoder out, flush it and decode the lead-in again, holding the loop's last frame meanwhile and dropping the loop's first frames for being late (a OnePlus with a Snapdragon: 100–140 ms and 2–3 frames for 120 frames of 1080p, 90–165 ms and up to 7 frames for 45 frames of 4K at 60 fps). So `ExoEngineFactory` says that such a clip starts on a key frame (`startsAtKeyFrame`): a loop goes on in the same decoder session, and the player's `LeadInVideoRenderer` keeps the lead-in off the screen.
    - From Android 14 the lead-in is queued as decode-only (`BUFFER_FLAG_DECODE_ONLY`): the decoder gives nothing back for it and runs through it while the loop's last frames wait to be shown, about seven frame intervals ahead. On that phone the seam is then one frame interval for 120 frames of 1080p; what the decoder can't finish in that time holds the last frame for the rest (152 frames of 4K AV1: 140–165 ms instead of 400–440).
    - Older Androids get the lead-in back and skip it frame by frame: no pause up to about a second of 1080p, about as long a pause as before beyond that.
    - Either way no frame before the start is shown, and none of the loop's first frames is lost: a lead-in that isn't done in time stops the player's clock (a moment of `STATE_BUFFERING`).
    - A loop's lead-in is queued with times of its own, right after the last loop's frames (`LeadIn`, tested on the JVM): on its own it would take the decoder back in time. Frames queued as decode-only count as the decoder's progress for the watchdog (`skippedInputBufferCount`).
    - The renderer leans on Media3's internals: it changes a buffer's time in `shouldDiscardDecoderInputBuffer`, the last call before that time is read. Check the seam on a phone after a Media3 update.
    - The lead-in is still decoded at every loop: a long one costs battery. «Optimised» has none.
  - A loop ends on a frame's time: where the first frame the clip doesn't show would have been shown (`cutEndUs`, tested on the JVM; `ExoEngineFactory` reads the frames' times around the end once, with `MediaExtractor`, and only for a clip that ends before its video does). Media3 cuts a clip at the first frame at or after its end in decoding order (`ClippingSampleStream`). In a video with B-frames the ones shown just before that frame come after it in the file and are cut off with it: the clip can't show them, and its last frame stayed for theirs too, at every loop (50 ms instead of 17 with three of them at 60 fps, 117 instead of 33 in an HEVC clip), so the loop ends where the first of them would have been. An end between two frames moves to the later one, and the last frame stays for as long as it does in the video: cut short, it cost a 24 fps clip the first frame of every other loop. A clip whose end is more than 600 frames after a key frame keeps its end: the extractor gives a frame's time only with its data.
  - Consumers hand it a surface and show the placeholder on `WallperPlayerState.Failed`.
  - `setVideoSurface` blocks until the decoder has let go of the previous surface, like ExoPlayer's, so the caller may release that surface right after.
  - `EngineSupervisor` keeps two engines, both created first thing in `run()` (on the player thread; ExoPlayer throws on any other): the active one on the surface and a standby one, prepared and paused without a surface. On a stall it releases the active one, hands the surface to the standby (`setSurface`, `seekTo`, `play`) and creates a new standby in place of the stalled one. Engines are recreated only at a switch and after a long pause (> 15 s, both are released); there is no background work.
  - `StallWatchdog` only reports a `StallCause`; it never fixes anything. The supervisor decides: switch to the standby, or `Failed` (content errors, or no standby left).
  - `RetryPolicy` paces switches: 4 with delays of 0, 1, 3 and 5 s before each, reset 30 s after the last one. A standby that broke while waiting is recreated at the switch and costs an attempt.
- **GL (`core:gl`).**
  - `VideoWallpaperRenderer` owns one video texture per EGL context and reports its surface through `onVideoSurfaceCreated`. A lost context's texture is released only after the new one shows a frame.
  - `RenderGuard` inside `WallpaperGLThread` repairs EGL.
  - The video engines don't call `play`/`pause` themselves: `VideoPlaybackControl` plays while the wallpaper is visible and nothing holds it (Battery Saver or severe heat, `PowerSaving`, if the user wants it: «Save battery», off by default), and applies `VideoPlayback` (loop; start over at each wake; once from the start at each wake, then `Ended` until the next one). A wake is the first play after the screen was off (`ScreenOffs`); coming back from an app or from Battery Saver isn't one.
  - An original video pans with the launcher's pages (`VideoWallpaperRenderer.pageOffset`, a uniform shift of the texture coordinates): `PageScroll` moves the crop window half its width across all the pages, along the screen's horizontal (turned with the crop), inside the frame, the chosen crop on the middle page when it fits. Processed videos don't pan: there's nothing beside their crop. The user's «Move with home screen pages» (`WallpaperSettings.scrollsWithPages`, off by default) is applied by the service for every wallpaper: off, engines are told there are no pages (`onOffsetsChanged(0.5, 0)`), so the black hole doesn't turn either; a new engine gets the launcher's offset right away.
  - A video frame and the launcher's offset each ask for a frame, and during a swipe that is more frames than the display shows: the window's buffer queue fills up and the picture trails the pages, unevenly. `VideoFramePacer` (`core:engine:impl`, tested on the JVM) draws one frame per refresh at most: an offset as it comes, straight from the main thread (the launcher sends one per refresh, just after the vsync, so it is the clock of a swipe), a video frame at the next vsync (`Choreographer` on the engine's callback thread) or with the swipe's next offset. A frame drawn past it (the one at `resume`, the render guard's redraw) costs that swipe one refresh more of delay.
  - A draw latches the newest video frame and passes over any that waited (`NewestFrame`, tested on the JVM): a `SurfaceTexture` hands its frames out one per `updateTexImage`, oldest first, and keeps the rest, so one latch a draw would show the video late for good, and fast whenever draws outnumber frames.
  - A picture (`PictureWallpaperEngine`, `PictureWallpaperRenderer`) is cropped, turned and panned like an original video, through the same `UVCoords` and `PageScroll`, on a 2D texture of only the part it can ever show (`PictureRegion`, tested on the JVM: the crop window wherever the page scroll takes it), subsampled as far as the screen and the texture limit allow, decoded as stored like the editor shows it. It is a still frame on a `WallpaperGLThread` of its own, like the placeholder's: drawn when the offset or the surface changes, no heartbeat; the bitmap goes once it is a texture and is decoded again after a lost context. A picture that can't be decoded shows the placeholder.
  - A tint is a uniform (`TintUniform`: `uTint`, the three factors, all ones without one) that the video's and the picture's fragment shaders multiply by on the way out: no blending, no pass of its own, nothing left in the GL state for `GlState.reset`. An optimised video that goes through GL (`asWholeFrame`) gets none: it is in its frames.
  - The video and black-hole engines reach their GL thread through a seam: `GlHost.open` gives a `GlLink` for the engine's renderer (`GlClient` makes one per GL thread). `OwnGl` is a thread of its own, a `RestartableGl`: what every wallpaper outside a series has. `SharedGl` is one thread for all the slides of a series (see «Series»).
  - A renderer says whether its last frame had the wallpaper (`GLWallpaperRenderer.hasPicture`: a video frame latched, the picture a texture, the black hole's shaders and tables there). A `gated` `WallpaperGLThread` shows no frame without it, so the window keeps what it had: the wallpaper before. A thread may also start before it has the window (`prepareOffWindow`: a 1×1 pbuffer, no swap; a device without one waits for the window) and move its context onto the window later (`RestartableGl.attach`), showing its first picture even while paused (`presentOnce`). All off for a wallpaper outside a series.
  - `RestartableGl` (`core:gl`) owns the GL thread of the video and black-hole engines: the heartbeat (it runs only while frames are expected, so a hidden wallpaper never wakes for it; the first frames after a shader compile get 10 s), restarts limited by `GlRestartPolicy` (3 per 2 min), the teardown on the callback thread. It replaces a thread only once it has exited: one stuck in the driver still holds the window, so the engine gives up. The video engine detaches the player (`setVideoSurface(null)`) before the old GL thread exits.
  - A wallpaper that gave up shows the placeholder until the user picks a wallpaper, that one too (`ActiveWallpaperSource.activations`), or until it is visible again 5 min later.
- Every ExoPlayer call happens on the player thread (`setLooper`). GL objects are touched only on the GL thread.
- The supervisor, watchdog, policies and `RenderGuard` are tested on the JVM, with virtual coroutine time or fake clocks and fake engines. Keep Android types behind `ManagedEngine` / `RenderRepairs`.

## Built-in wallpapers and the black hole (see BLACKHOLE_PLAN.md)

- A built-in wallpaper is a row of `wallpapers` with `built_in = BuiltInWallpaper.key`. `built_in` has a unique index (schema v3), and the database seeds missing built-in rows on every open (`SeedBuiltInWallpapersCallback`, `INSERT OR IGNORE`); they are listed first (`ORDER BY built_in IS NULL, id`), activate like any wallpaper and are never deleted (the use case refuses too). Never rename a `BuiltInWallpaper.key`.
- `WallpaperSpec` is sealed: `Media`, `ProcessedVideo` or `BuiltIn`. A built-in's feature binds a `BuiltInWallpaperProvider` (`core:engine:api`) with `@IntoSet`: its engine, colours, list stills and whether the device can draw it. The service, `WallpaperEngineFactory`, `BuiltInPreviews` and `LiveWallpaperController.isSupported` look it up by key (`BuiltInWallpapers`); a key without a provider shows the placeholder. A new built-in needs no change in core beyond its `BuiltInWallpaper` key.
- Every tunable of the black hole lives in `BlackHoleParams` (`feature:blackhole:logic-api`). Defaults start from BLACKHOLE_TZ.md §10; the look was tuned on a phone (BLACKHOLE_PLAN.md §9). User settings are applied on top with `BlackHoleSettings.applyTo`.
- `BlackHoleSettings` (`logic-api`, with its ranges) is `@Serializable`. `BlackHoleSettingsStore` keeps it as one JSON string in device-protected SharedPreferences, only the fields that differ from the defaults. A new setting is a new field with a default: old JSON still reads, unknown keys are ignored. Never rename a field; its name is the stored key.
- Lens tables depend only on `(r_c, N_α, N_φ, K)`. `LensTablesRepository` generates them once and caches them in device-protected `cacheDir/blackhole` (`LensTableFiles`: every quality of the current r_c, K and format). Nothing keeps them in memory: the renderer drops its copy once they are on the GPU and asks again after a lost context (`onTablesLost`). Bump `LensTables.FORMAT_VERSION` when the layout or the physics changes.
- Built-ins the device can't draw (no ES 3.0) are hidden from the list (`LiveWallpaperController.isSupported`).
- The camera orbits about the disk axis; the gyroscope and the launcher turn it on top in screen axes (`CameraPose.turned`), then the elevation is clamped. Their recoil is a principal-point shift (`FrameState.recoilX/Y`, half screen heights). The settings preview's drag turns the orbit itself (`setOrbitOffset`), with no recoil.
- `BlackHoleRenderer` (GL thread only) is shared by the wallpaper, the list preview (`BlackHolePreviewRenderer`, EGL pbuffer) and the settings and debug screens. The screens see it as `BlackHoleFrameRenderer` from `BlackHoleRendererFactory` (`logic-api`), handed to the preview through `LocalBlackHoleRenderers` by the navigation entries. Frames are paced by `Choreographer` on the engine's callback thread; animation phases come from `Long` nanoseconds, never a growing float.
- The setting «Optimised rendering» (`FrameParams.optimizedShaders`, on by default) picks the `OPTIMIZED` shader paths: the disk shaded only where a ray crosses it, a texel-for-texel composite at scale 1, no trigonometry per crossing, cheaper star maths. The original paths stay behind `#else` to compare; keep both compiling (the shader script checks both).
- The sky lens: `LensParams.strength` scales the physical bending (1 is physical), and `fadeStart`/`fadeEnd` (shadow radii, infinite end by default) fade it out; the shadow and the disk images stay physical. The settings' «Shape the lens» switch applies its three sliders; off keeps the defaults.
- `FrameParams.maxRenderScale` (the «Render resolution» slider) caps the quality level's render scale (`effectiveRenderScale`). Star σ is in screen pixels, so a lower scale only softens the stars.
- Hidden, the black hole does no work: no frames, no gyroscope, no GL heartbeat, and new lens tables (heat, settings) wait until it shows again. Only listeners that cost nothing until they fire stay registered.
- Frames are paced by a whole number of vsyncs (`FramePacing.vsyncsPerFrame`). A still frame (power save, heat) wakes only for an input that moves the picture, and the frame that draws it starts the power-save parallax.
- Shaders live in `feature/blackhole/logic-impl/src/main/assets/blackhole` (`#include` is resolved by `ShaderLibrary`). After editing them run `./gradlew validateBlackHoleShaders` (also part of `check`): it compiles them for every quality level without a device, as GLSL ES 3.00 with glslangValidator, or as 3.10 with the NDK's glslc when that is all there is.

## Series

- The «+» asks (`AddWallpaperDialog`, no title: each option says with an icon, in the accent and without a badge, and a line where it starts from): a new wallpaper from the gallery, or a new series of the wallpapers there are (offered only while there are two it could pick: no groups, no built-in the user hides, even the active one). `WallpaperGroupDestination(groupId)` is one screen with one ViewModel and three steps (`Navigator` has no results): pick (the list's `WallpaperCard` with `selected`: tinted in `primary` with a check in the middle; no groups, hidden built-ins only if they are members; a FAB with the same check confirms, coming up from below while anything is ticked and going back down when nothing is, greyed out (`FAB(enabled)`) with a hint beside it saying how many more until two are) and arrange (members in order, swiped aside to take them out, held to drag them to another place (`MemberDrag`: the row follows the finger, the ones it passes the middle of make way with a tick, the list scrolls by itself held near an edge; `MemberOrder` tested on the JVM; the dropped order goes to the reducer, and the list shows it until the members are that order), a hint saying so on the first three visits only, `SwipeHintMemory` in device-protected prefs, read before the members show; without members an empty state in the middle, the button under it; on a panel below them the time each shows from `SlideDuration.CHOICES`, the chips beside their title, the transition where series have them, and save, from `GroupEditorState.MIN_MEMBERS` on), and the transition (see below). The steps slide as the app's screens do (`GroupEditorState.stepGoesBack`: one that opens comes from the right, one that closes goes back to it). A new group starts on pick, an edited one on arrange; «Add wallpaper» goes back to pick with the members ticked, and back from there changes nothing; the members' list state lives above the steps, so they come back scrolled where they were. `SaveWallpaperGroupUseCase` makes a new group active like a new wallpaper. «Series» is the name the user sees; the code says group for the data and series for the engine.
- A member row is its picture across the whole row, cropped to its middle, with the list card's label bottom right and its pencil top right (`WallpaperPicture`, `KindLabel`, `CornerEditButton`, shared with `WallpaperCard`): the editor, or a built-in's settings (`settingsDestination`, shared with the list), none for an optimised video. The series waits under it as it is, saved or not, and shows what the editor saved.
- «Add wallpaper» (`AddWallpaperButton`) works like «Add currency» in NomadRates' favourites conversion: a spacer at the end of the list keeps its place and the button is drawn over the list there, a pill. Once scrolling takes that place down to the panel, it stays there (`AddButtonPlacement`) and morphs into a round plus; at the end of the list the list picks it up again. A press pops it. While the list doesn't scroll the button springs to where it belongs (`AddButtonPlacement.top`), as the members move when one is taken out, or under the empty state when the last one is; while it scrolls it moves with the list exactly. Wherever the button comes near the panel (elevated, no fade above it), pill or round, the panel cuts a cradle round it into its top edge (`CradleShape`, Material's FAB cradle drawn apart to the button's width: round ends joined by a straight bottom, and by fillets to the edge; maths in `CradleGeometry`, tested on the JVM), deeper as the button comes down, the deepest when it is pinned. The panel reads it in its `graphicsLayer`, so it follows the scroll and the morph without recomposing. A shade in the background's colour (`ListEndShade`, invisible over the background itself) darkens the list's end towards the panel, behind the panel and the button. The list runs on behind the panel to a little below the deepest cradle, so it shows through the cradle and nowhere below the panel. The overscroll stretch is drawn by one layer around the list, the panel and the button, so the button never comes apart from the list. Android 9 and older draw no shadow for a concave outline: there the panel has none while the cradle is open.
- A series' picture in the list (`MakeSeriesPictureUseCase`; `SeriesPictures`, `feature:wallpapers:logic-impl`) is its first four members' pictures side by side, parted by lines that lean 20° right going up, each through its share of the width at mid-height (`SeriesPictureLayout`, tested on the JVM); each picture covers its part's box, decoded as stored like the wallpaper's, without its member's tint, as the cards show it. A series of one shows its member's own picture. Pictures are kept in device-protected `files/previews/series` as `<group id>_<key>.webp`, the key a CRC of the members' picture files (path, size, time) and of `FORMAT_VERSION` (bump it when the drawing changes): made only when missing, the group's older one deleted once the new one is ready, all of a group's by `DeleteWallpaperUseCase` when it goes. The list makes one once every built-in among the members has its preview (a black hole's preview is named by its settings, so new settings make a new picture); a built-in this device can't render leaves its part empty.
- `SeriesWallpaperEngine` (`core:engine:impl`) is the schedule only: which slide and when. It shows one slide at a time through its `SlideStage`, and replaces it after `SlideDuration` of visible time; with `SlideDuration.ON_WAKE` at each screen-off, so the switch never shows. Not at the broadcast itself, which comes as the screen starts to go off, before its animation: the switch waits until the service hides the wallpaper, or `HIDE_WAIT` (2 s) at most for a device that keeps it «visible» under the always-on display, and happens only while the screen is still off (`ScreenOffs.isScreenOn`); a screen back on first keeps the slide for that wake. The launcher's offset and zoom are replayed to each new slide. A slide that gives up (its own `EngineHost`) is skipped from then on; when all have, the service shows the placeholder. The service takes the system colours from the first slide, once: on Android 12+ each change re-themes the phone. Tested on the JVM with fake engines and virtual time.
- How a slide gets onto the screen is its `SlideStage`'s business. `CutStage` cuts: it releases the slide's engine (which lets go of the surface before returning) and only then creates the next, a cut; an original video's first frame after it is black until the decoder gives one. Two more change slides without a seam, picked by `SeriesSwitch` (`AppSettings.seriesSwitch`, a debug row in the settings, which only debuggable builds show): `SHARED_GL` is the one meant to stay and the default, release builds included, `WARM_ENGINES` is kept to compare with. `WallpaperSettingsSourceImpl` hands the service what is stored; the picker's preview always cuts, and the service makes the series' engine anew when the choice changes. Both use `WarmStage`: `WarmStage.LEAD` (2 s) before a slide's time is up the schedule has the next one made off screen (`prepare`), beside the one that shows, and the switch waits for its picture (`PREPARE_TIMEOUT`, 5 s at most; then it is shown as it is, and the gate keeps the old frame until its picture comes). Two slides live only for that long: the old one is released right after the switch. With nothing prepared (the first slide, `ON_WAKE`'s switch while hidden, a slide that gave up) the old slide is released first and the new one shows its first picture once, paused. A slide that gives up while it is prepared is let go of and tried again alone at its turn; only on screen does it count as failed. A hidden wallpaper prepares nothing (`dropPrepared`).
  - A slide made off screen is one of the usual engines given a `SlideStart` (`core:engine:api`: the `GlHost` and whom to tell once its picture is drawn): it starts hidden, its player keeps one decoder (`keepsStandby = false`: the spare is made when a stall needs it) instead of two, and it takes the screen at `WallpaperEngine.show()`. Pictures have `PictureSlideEngine` (decoded on its own thread); a built-in comes through `BuiltInWallpaperProvider.createSlide`, and the black hole warms up (tables, shaders, one frame) and appears whole, without its fade from black.
  - `SeriesSwitch.WARM_ENGINES`: every slide on `OwnGl(offWindow = true)`, a GL thread of its own that prepares on a pbuffer. At the switch the old slide pauses and lets go of the window (`onSurfaceDestroyed`), the new one takes it. An optimised video keeps its direct output: prepared without a surface (`awaitPrepared`), it gets the window at `show()`, and moving its decoder there holds the old frame for a few frames.
  - `SeriesSwitch.SHARED_GL`: every slide's renderer on `SharedGl`, one GL thread, context and window surface for the series. `SlidesRenderer` draws the slide on screen with that slide's own renderer and lets the next one draw unseen, and resets the GL state (`GlState.reset`, the pending errors too) whenever the context passes from one renderer to another: each was written to have a context to itself, so a renderer that binds more (vertex array objects, pixel buffers) must be reset there as well. A switch is the thread's next frame. Optimised videos go through GL there, as a whole frame. A renderer that throws is given up on alone; a GL restart has every slide make its renderer anew on its own thread; when the shared thread can't be restarted the whole series shows the placeholder.
- Transitions (`SlideTransition`, `core:model`: a `TransitionEffect` and its 400–2500 ms, 1 s by default, `Wallpaper.Group.transition`, `WallpaperSpec.Series.transition`) blend one slide into the next, only with `SHARED_GL`: every other series cuts, and a series keeps the transition it has while they aren't offered. With one, `SlidesRenderer.show` keeps the slide it replaces («leaving»): until the new slide has its picture the old one stays on screen and goes on playing; from then each frame draws the two with their own renderers into a target each (`TransitionCanvas`: two RGBA textures of the window's size behind framebuffers, made when the blend starts and deleted when it ends) and blends them onto the window (`TransitionShaders`, GLSL ES 1.00 for any context, one pass with two textures; the frames of the blend ask for the next themselves). Renderers draw into whatever framebuffer is bound: the black hole reads `GL_FRAMEBUFFER_BINDING` as its output. A canvas that fails is given up on, and that series cuts. `WarmStage` keeps the old slide's engine playing for `WarmStage.handoverOf` the transition (its duration and 500 ms) after a switch to a slide that was ready, while visible; otherwise it cuts as before. A hidden wallpaper, another switch or a surface change let the old slide go at once.
- The series' panel has a «Transition» row with the one chosen (only where they are offered: `WallpaperSettingsSource`'s `seriesSwitch` is `SHARED_GL`; later a remote config). It opens the transition step (`TransitionStep`): the first two members (`GroupEditorState.PREVIEW_MEMBERS`) going one into the other and back through the transition, round and round, each alone for 2 s between, in a phone frame with the screen's proportions (`PhoneFramedScreen`, `core:designsystem`, the editor's frame; the picture is clipped to the screen's rounded corners); on a panel below the effects in a row of chips (`ChoiceChipRow`, shared with the slide durations) and the duration on a slider. No timeline to move along: how a transition looks has nothing to do with how long a member stays on the wallpaper, an hour maybe. A pick shows at once: the loop starts again with it. Back keeps the pick; Save saves it with the series.
- The preview is a path of its own, so that nothing of the wallpaper's engines, schedule or players is touched for it (`SeriesPreview`, `core:engine:api`, plays and pauses; `core:engine:impl` package `preview`): every frame is `SeriesTimeline.at` its position (`core:model`, tested on the JVM: each slide alone for the hold, then the transition into the next, the last one's into the first; a slide's own time starts with the transition that brings it in and runs on under the one that takes it away, as on the wallpaper), the position moving with the clock while it plays. Each slide is the wallpaper's own renderer and what moves it in its time (`PreviewSlide`): a video an ExoPlayer of its own (`createLeanExoPlayer`, the clip clipped and looped) into the texture of `VideoWallpaperRenderer`; a picture `PictureWallpaperRenderer`; a built-in a `BuiltInScene` (`BuiltInWallpaperProvider.createScene`; the black hole's `BlackHolePreviewScene`: its renderer at the picker preview's quality, `BlackHoleScene.frame` at the slide's time, its tables handed over at its next frame). Only the slides around the position live (those on screen, the one before, the one coming next: three players at most). `SeriesPreviewGl` (`core:gl`) is one GL thread on the screen's `TextureView` (through a `SurfaceHolder` over its surface) with a `PreviewCompositor`: one slide into the window, or two into the `TransitionCanvas` targets mixed at the progress the timeline gives (tested on the JVM with fakes); a slide without its picture yet leaves the other one alone, a renderer that throws is left out, a canvas that fails makes the preview cut.

## Editor crop

- `CropRect` is in upright media pixels and has a `rotation`: the picture turned clockwise on the screen, in degrees; the area is the rect turned about its centre by -rotation, so the rect itself may reach past the frame (`crop_rotation`, schema v5). The GL quad (`UVCoords`, `CropCorners`), the page scroll and the export (`CropMatrix`, one `GlMatrixTransformation` in place of Media3's `Crop`) all turn it.
- `CropEditor` (`feature:editor:ui-impl`, package `crop`) is a still phone frame (`PhoneFrame`, `core:designsystem` with `FrameBounds` and `PhoneFramedScreen`, shared with the series' transition step: body, three side buttons that follow its height, a fixed-size cut-out) whose screen has the proportions of the device's screen, as large as fits the area inside `CropEditorDefaults.FramePadding`, centred. The picture moves under it: drag, pinch and turn (`detectCropGestures`; turning starts after 5° of twist, so a pinch doesn't tilt it). The state follows the fingers unsnapped and shows them snapped (`CropGeometry.snapped`): the angle level, to a multiple of 90°, within 4° of it (turned about the picture's centre), and the picture's centre to the frame's middle along each axis, within 3% of the frame's shorter side. Each new snap is a tick (`OnCropSnapped`, which the ViewModel hands to `Haptics`); a picture that starts level or centred doesn't tick for it. Dashed yellow lines through the frame's middle show the snaps while the fingers move (`CropState.guides`): across for level (once the fingers have turned) or centred up and down, up and down for centred across. When the fingers let go it springs to the nearest placement that covers the whole screen (`CropGeometry.covering`: scaled up about the frame's centre only as much as needed, then moved as little as needed), zoom limited to 8× the covering scale. Around the frame the picture is dimmed and fades into the background; while fingers are down a rule-of-thirds grid fades in.
- The picture is laid out once at the covering scale; gestures change only its `graphicsLayer`. `CropState` keeps the `Placement` (scale, rotation, offset from the frame's centre) and gives the crop to save (`crop()`); a crop the user didn't touch is given back exactly. Its maths (`CropGeometry`, `FrameBounds`) is tested on the JVM.
- The reset button, right of the playback buttons, appears while anything differs from what the editor opened with: the crop (`CropState.isChanged`), the trim, the tint or the original / optimised choice (`EditorState.hasEdits`). It springs the picture back the short way round (`CropState.reset`; an edited wallpaper gets its saved crop back exactly) and `OnResetClick` resets the rest.
- Pictures show under the frame decoded as stored (no EXIF orientation), like their media info's size.

## Editor preview and the trim bar

- `TrimBar` (`core:designsystem`) knows nothing of video: the playhead stays at its centre, it reports scrubs and handle moves (`onSeek`, `onTrimChange`) between `onDragStart` and `onDragEnd`, and reads the position through a lambda while drawing. Its geometry lives in `TrimBarMath.kt` and is tested on the JVM.
- `EditorPlayer` is one ExoPlayer with the whole video, so a handle can show any frame. It plays from the playhead, or from the start of `EditorState.trim` once it has reached its end, and stops at that end itself (`OnPlaybackEnded`): no loop. It plays while `isPlaying` (the user's choice, off when the editor opens), no drag is on and no export runs; drags turn on scrubbing mode. Pictures get no player.
- The buttons beside play put the start or the end of the trim at the playhead (`OnSetTrimStartClick`, `OnSetTrimEndClick`). A button is on only while the playhead is inside the kept part, not on a boundary, and would leave at least `TrimBarDefaults.MIN_DURATION_MS` (`withStartAt`, `withEndAt`): the buttons narrow the kept part, the handles widen it. The reducer checks again. It follows the playhead through `derivedStateOf`, so the controls recompose only when a button turns on or off.
- A player error goes to `Timber.e` and, as `OnPreviewFailed`, to the editor's error dialog; closing it leaves the editor, like media that can't be prepared.
- The strip's frames are key frames from `MediaMetadataRetriever` on `Dispatchers.IO`, one per tile within a pixel budget (`rememberVideoFrames`), held while an export runs.
- The player, its position and the frames live in the screen's composition, not in the ViewModel: the position changes every frame, which `runningFold` shouldn't carry, and frames are Bitmaps, which `logic-api` (plain Kotlin) can't. `EditorState` keeps only what the save and the user's choices need: `trim`, `isPlaying`, the processing toggle and the save under way.
- «Original / Optimised» (`OptimisedToggle`, left of Save, for videos only) is hand-made: Material's expressive `ToggleButton` isn't in Material 1.4. Its «?» opens the explanation (`ProcessingInfoDialog`), and so does the first switch to optimised if it was never shown: the switch happens only on its OK, back leaves «Original». Save never waits for it. Shown counts as seen, remembered by `ProcessingInfoMemory` (device-protected prefs). The ViewModel starts a save by following `EditorState.save`.
- An optimised save shows `ExportProgressDialog` while Transformer exports: what it makes (`ExportOutput`: the crop's size as shown, the clip's length and the codec, which `TransformerVideoExporter` knows itself; an encoder that can't take the size falls back, `onFallbackApplied`, and the size follows), the percent (all Transformer tells while it works, polled twice a second) and the time left at the pace since the first percent (`ExportPace` in the exporter: the start, the codecs starting, says nothing of the rest; nothing before 3 percents and 1.5 s past it; tested on the JVM, like `ExportTimeLeft`, which says it). Only its Cancel closes it (`OnExportCancel`): the reducer lets go of the save, which stops the export (`flatMapLatest` in the ViewModel, `Transformer.cancel` in `awaitClose`), and drops what the export still sends on its way out. Once the export is done the save runs to its end whatever happens (`NonCancellable`): halfway, it could leave a wallpaper whose files are gone.
- `ClipRange` with an end not after its start plays to the end of the video (`endMsOrNull`): the editor saves `0..0` when it doesn't know the length.

## Editor tint

- The tint button sits left of the playback buttons, 16 dp from the edge like the reset button on their right (a picture has only the two). It is a plain icon button, without a container whether the picker is open or not: only the icon's colour changes, to the accent while it is open.
- It changes what is under the buttons: the trim bar and the save row go, the tint's picker and its switch (`TintPanel`) rise from the bottom edge. The switch's row says «Tint enabled» or «Tint disabled», one fading into the other. Pressed again, or the system's back (`BackHandler`, `OnTintClose`), brings the trim bar and the save row back: there is no save while the picker is open.
- `EditorLayout` (a custom `Layout` in `EditorScreen`) does it, reading the progress (0 to 1, an `animateFloatAsState`) only while laying out, so the way recomposes nothing. The crop is always laid out for the room it has over the trim bar and the save row, which stay in the composition under the picker so that their height is known. When the picker leaves less room the crop is drawn smaller as a whole, in a layer scaled about its middle (`CropEditorDefaults.scaleToFit`, `FrameBounds.scaleToFit`, tested on the JVM): the frame keeps its proportions (border, buttons, cut-out), and since nothing inside is laid out again, the picture, the gestures and the crop to save are exactly what they were. Don't refit the frame to the smaller room instead: its border, buttons and cut-out keep their size in dp and look wrong on a smaller body.
- `EditorState.tint` is a `TintChoice`: the picker's colour (`HsvColor`) and whether the tint is on, off for a new wallpaper. The colour stays while it is off, so the switch brings it back; the first switch gives `TintChoice.DEFAULT_COLOR`, black at 30 %. A touch on the picker switches the tint on (`OnTintColorChange`): the colour would change unseen otherwise. What is saved is `TintChoice.tint`: null while off or fully transparent. `hasEdits` compares that with the saved wallpaper's, and reset goes back to it.
- How dark the picture gets is the picker's alpha (how much of the tint is applied) and how dark the colour itself is (down the area): any hue goes all the way to black.
- The preview shows the tint with `Modifier.wallpaperTint` on a box over the whole picture, inside `CropEditor`'s picture slot, so it moves with the picture: what the renderers and the export do in their shaders.
- `ColorPicker` (`core:designsystem`) knows nothing of wallpapers and keeps nothing: one canvas with the saturation and value area, the hue bar and the alpha bar on one rounded card, a thumb each; a touch puts the thumb there without waiting for a drag, and a drag stays with the part it started on. The card is inset by what a thumb at an edge reaches out, so every thumb is inside the picker's bounds. Only the two bars (and the area's bottom edge, as far as its thumb reaches) are kept from the system's edge gestures (`systemGestureExclusion`), so that a thumb at the screen's edge can be dragged; a swipe from the edge anywhere higher is still «back» and closes the picker. It holds the colour as `HsvColor`, not as red, green and blue: a grey has no hue and a black no saturation, and the thumbs would jump back. `HsvColor` to a packed colour and back is exact, so a saved tint doesn't drift when it is edited. Geometry in `ColorPickerMath.kt`, tested on the JVM.

## Diagnostics (`core:diagnostics`)

- `Timber.w` is a breadcrumb and `Timber.e` a crash report: `ReportingTree` in `:app` forwards both to `Diagnostics.reporter` (`CrashReporter`). Log a failure the app recovers from with `Timber.e`, and the reason in the message.
- `Diagnostics.reporter` is global on purpose: GL threads and engines aren't built by Hilt, and it must work in direct boot. Context keys: `gl_renderer` (`WallpaperGLThread`), `black_hole_quality`.
- Firebase (Crashlytics, Analytics) is in release builds only (`releaseImplementation`, the build type's code in `app/src/release` and `app/src/debug`): debug builds neither carry nor start it. Release builds report to Crashlytics (`FirebaseCrashReporter`) and to logcat (`adb logcat -s WallperReport`, read by the in-app report). Crashlytics keeps its files in credential-encrypted storage: Firebase starts it after the first unlock, and the reporter doesn't touch it before (`isUserUnlocked`), so reports in direct boot reach logcat only.
- «Share usage and crash data» (`AppSettings.shareUsageAndCrashData`, on by default) turns Analytics and Crashlytics collection on and off: `installDiagnostics` in `app/src/release` applies it to Firebase, which keeps it across runs, once the user has unlocked. While it's off the reporter sends nothing to Crashlytics; crash reports Crashlytics kept meanwhile are deleted (`deleteUnsentReports`) before it turns back on. Debug builds show the switch, with nothing to turn off.
- `ExitReasons` reports crashes and ANRs of earlier runs from `ApplicationExitInfo` (API 30+), once the user has unlocked: before, a report reaches logcat only and would still count as reported. Crashlytics doesn't see native crashes, nor any before the first unlock.

## MVI (`core:mvi`)

- `BaseViewModel(initialState, reducer)`: every event is folded by the reducer through `runningFold`. The event buffer is unbounded, so no event is dropped.
- Side effects live in the ViewModel's `eventFlow.onEach { when (event) ... }`. Their results come back as internal events through `onEvent(...)`.
- An effect takes its data from its event, never from `state.value`: the reducer folds the same event on another collector, and which one runs first isn't guaranteed. An effect that follows the state collects `state.map { ... }.distinctUntilChanged()`.
- One-off UI effects (Toast, starting an Intent) are events the screen collects from `eventFlow`. Navigation goes through the injected `Navigator`.
- The reducer is pure and returns `state` for side-effect-only events. Screens are stateless `(state, [eventFlow], onEvent, modifier)`.
- Test the reducer directly. Test the ViewModel with hand-written fakes and `Dispatchers.setMain(UnconfinedTestDispatcher())`. No mocking library.

## Adding a screen

1. `ui-api`: `@Serializable data class/object XDestination : Destination`.
2. `ui-impl`:
   - `XState : State`, `XEvent : Event`, `XReducer @Inject constructor()`;
   - `@HiltViewModel XViewModel`; use an assisted factory when it needs the destination;
   - `XScreen`.
3. `ui-impl/di/XUiModule`: `@Provides @IntoSet fun provideXEntry(): FeatureEntry<*> = featureEntry<XDestination> { destination, modifier -> ... }`.
4. `:app` depends on the new `ui-impl`, plus its `logic-impl` if there is one.
5. Reducer and ViewModel tests.

File names must be unique across the modules of one feature: they share a Kotlin package, and clashing `*Kt` classes break dex merging.
