# Ревью `dark_star`: сводное решение трёх ревьюеров

> **Как проводилось.** Три независимых ревью: senior Android developer (DEV), senior Android architect (ARCH) и tech lead (TL). Затем раунд дебатов, в котором каждый разобрал находки двух других. Сводное решение написал TL с учётом всех ответов.
> Ревьюеры смотрели незакоммиченные изменения ветки `dark_star` против `f03b9c9` и закоммиченный код. Всё установлено чтением кода, Gradle ревьюеры не запускали. Код не менялся.
> Исходники в папке `code-review/`: ревью (`1-review-dev.md`, `2-review-arch.md`, `3-review-tl.md`) и ответы в дебатах (`4-…`, `5-…`, `6-…`). ID в скобках — номера находок оттуда.

## 1. Итоговый вердикт

> **Коротко.** В `main` мержить можно, но только после страховочного коммита и разбиения на 3 коммита (фаза 1). Релизить нельзя: мешают три критичных бага, подпись релиза, отсутствие отчётов о падениях и незамеренная батарея (фазы 2–4).

- **Мерж.** Около 7 тыс. строк ни разу не закоммичены. Изменение `core:gl`, которое меняет поведение видеообоев, смешано с чёрной дырой. После фазы 1 мержить можно: приложения нет в сторе, и `main` не продакшен.
- **Что блокирует релиз:**
  - вечная заглушка: на API 29 при перегреве, повторный тап её не снимает (группа 1);
  - утечка GL-потока, если рестарт GL совпал с `release()` (группа 2);
  - краш редактора — он уже в закоммиченном коде (группа 3);
  - release подписан debug-ключом, AAB нет (группа 5);
  - отчётов о падениях нет, поэтому всё самовосстановление в проде работает вслепую (группа 6);
  - батарея не замерена, а это обои, которые видны всегда (группа 7).
- **Фаза 5** релиз не блокирует, но до релиза она дешевле. После релиза хранение настроек и схема БД потребуют миграций.

## 2. Подтверждённые факты

> **Коротко.** Здесь только то, что проверили в коде минимум двое. DEV-7 — гипотеза с высокой уверенностью, на устройстве её не проверяли.

- `BlackHoleWallpaperEngine.kt:353` — на API < 30 `applyFrameRate` выходит раньше присваивания, и `appliedFrameRate` навсегда остаётся −1. Пульс (`:401`) из-за этого не видит режим STILL. На API 29 при SEVERE: 3 рестарта GL, затем заглушка (DEV-1).
- `WallperWallpaperService.kt:87, 172-176` — `failedWallpaper` сбрасывается, только когда приходит другой `WallpaperSpec`. Повторную активацию тех же обоев гасит `distinctUntilChanged`, и заглушка остаётся до смерти процесса (TL-5).
- `BlackHoleWallpaperEngine.kt:194-211, 409-424`, `GLWallpaperEngine.kt:113-125, 144-159` — `released` проверяется только на входе в `restartGl`. `release()` гасит старый поток по таймауту, а новый создаётся уже после этого, и его никто не останавливает (DEV-2).
- `BuiltInPreviewsImpl.kt:38` — имя PNG строится из `settings.hashCode()`. В настройках есть enum, а `Enum.hashCode` даёт identity-хеш, разный в каждом процессе. Итог: на каждом холодном старте превью рендерится заново (DEV-4).
- `WallpapersViewModel.kt:41, 90` — превью запрашивается один раз на ViewModel. Она жива под экраном настроек, поэтому после правки настроек в карточке старая картинка (DEV-3).
- `feature/editor/ui-impl/.../cropper/Player.kt:32-42, 63-67` — длительность берётся через `postDelayed(2000)`. Если плеер не успел подготовиться, приходит `TIME_UNSET`, затем `setStart/EndPositionMs(<0)`, `IllegalArgumentException` и краш (DEV-5).
- `BlackHoleSettings.kt:227` и `LensTables.kt:19` — стор читает дистанцию как Float (44.20000076…), а `BlackHoleSettings()` даёт ровно 44.2. Имя файла таблиц содержит Double целиком. Поэтому «Сброс» и следующий запуск дают по лишней генерации таблиц (DEV-17).
- `app/build.gradle.kts:31` — release подписывается debug-ключом (TL-1).
- `WallperApplication.kt:21` — Timber работает только в DEBUG, репортера падений нет (TL-3).
- `CLAUDE.md:9` и `core/blackhole/physics/build.gradle.kts:4` — каноническая команда `testDebugUnitTest` не запускает JVM-модули, то есть 45 тестов physics не гоняются (TL-6).
- `DebugControls.kt:59` (0..12) против `BlackHoleSettings.kt:136` (0..10) — диапазоны уже разошлись. В `BlackHoleSettingsScreen.kt:73` HUD показывается в release без условия (TL-8).
- `scripts/validate_blackhole_shaders.py:48-49` проверяет `310 es` с одним набором define'ов, а `Gl.kt:18` собирает `300 es` (TL-7).
- `BlackHoleWallpaperEngine.kt:320-335` — `onVsync` перепланирует себя на каждый vsync. На 120 Гц это около 90 пустых пробуждений в секунду ради 30 fps (DEV-11).
- `WallperWallpaperService.kt:189-193` — цвета чёрной дыры отдаются для любого `BuiltIn` (ARCH-6, TL-12).
- `WallperWallpaperService.kt:92` — `stateIn(null)` смешивает «ещё грузится» и «обоев нет». При каждом старте сервиса заглушка создаётся и тут же выбрасывается (DEV-18).
- `PlaceholderWallpaperEngine.kt:51-52` — `onSurfaceDestroyed` вызывается без `waitMs` (ARCH-12).
- `core/storage/.../MediaStorageImpl.kt:18-20` — thumbnails и temp лежат во внешнем хранилище, а не в DE (ARCH-11).
- `ModuleBoundaries.kt:60-80` — проверяются только 4 правила из обещанных в `CLAUDE.md`. Публичные классы есть в `editor/ui-impl/.../cropper/` и в `WallpaperEngine.kt:3` (ARCH-5).
- `CLAUDE.md:4`, `ModuleBoundaries.kt:31`, `WallpaperEngineFactory.kt:41`, `WallpapersScreen.kt:141`, `EditorDestination.kt:9` ссылаются на `ARCHITECTURE_MIGRATION.md`, удалённый в `f03b9c9`. Из `.md` в git отслеживается только `CLAUDE.md` (TL-10).
- `core/player/.../ExoPlayerFactory.kt` нигде не используется (ARCH-18).
- `LensTablesRepository.kt:34, 75` — до двух таблиц, это до ~16 МБ, навсегда остаются в куче процесса обоев (DEV-9, ARCH-13).
- **Гипотеза (DEV-7).** Если поток завис в драйвере, рестарт создаёт второй EGL-surface на окне, к которому ещё подключён брошенный surface. Дальше `EGL_BAD_ALLOC`, заглушка тоже не может подключиться к окну, и получается чёрный экран.

## 6. Вопросы владельцу

> **Коротко.** Пять решений, которые принимает только владелец. Для каждого указана рекомендация команды.

1. **Качество по умолчанию.**
   - **Рекомендация:** AUTO и сохранять уровень, на котором он остановился. На OnePlus он останется на HIGH.
   - **Если всё-таки HIGH:** пусть HIGH тоже шагает вниз при перегрузке GPU — по сути это нынешний AUTO.
   - **Минимум:** чистый HIGH, но с выключенным GPU-таймером (DEV-13).
   - **Отдельно:** без GPU-таймера AUTO сейчас уходит на Medium. Предлагаем в этом случае держать стартовый уровень и полагаться на thermal.
2. **Режим энергосбережения.** Рекомендация: показывать неподвижный кадр (`powerSaveStill = true`). Включать после фикса DEV-1.
3. **Репортер падений.**
   - **Рекомендация:** Sentry за портом `CrashReporter`. Автоинициализацию выключить, `init` вызывать вручную в `Application.onCreate` с кешем в DE-хранилище. Плюс Play vitals — бесплатно.
   - **Альтернатива:** Crashlytics. Подключить проще, но до первой разблокировки после перезагрузки отчётов не будет, хотя обои в это время уже видны на экране блокировки. Падения в этом окне покроет только Play vitals.
   - В обоих случаях нужна декларация в Data safety. Как Sentry ведёт себя в direct boot, нужно проверить на устройстве.
4. **Состав «Основных» на экране настроек.**
   - **Предложение для «Основных»:** качество, гироскоп вкл/выкл, параллакс лаунчера вкл/выкл, чувствительность гироскопа, скорость диска, наклон камеры, экспозиция, количество звёзд и «Перемешать».
   - Всё остальное — в свёрнутые «Расширенные».
5. **Бэкап в v1.**
   - **Рекомендация:** `allowBackup="false"`. Видео в DE, скорее всего, превысят квоту в 25 МБ, а восстановленная БД без файлов бесполезна (гипотеза).
   - **Альтернатива:** бэкапить только настройки.
