# WallperPlayer: дизайн устойчивого плеера

> **Коротко.**
> - **Для потребителя это обычный плеер.** `WallperPlayer` отдаёт `setVideoSurface`, `play`, `pause`, `release` и `state`. Движков наружу не видно.
> - **Внутри два готовых движка.** `EngineSupervisor` создаёт оба сразу при старте: активный на поверхности и запасной — подготовленный, на паузе, без поверхности. При зависании поверхность уходит запасному, а вместо зависшего создаётся новый запасной. Кроме этого движки пересоздаются только после долгой паузы, фоновой работы нет.
> - **Сторож только сообщает.** `StallWatchdog` говорит, что и почему встало, и больше ничего не делает. Решает супервайзер: переключиться на запасной или сдаться (`Failed` → заглушка).
> - **GL отдельно.** Одна текстура на EGL-контекст, ремонт EGL, пульс GL-потока и свой лимит перезапусков. С плеером GL связывает только `setVideoSurface`.

Связанные документы: [STALL_GUARD_RESEARCH.md](STALL_GUARD_RESEARCH.md) — причины зависаний; [CLAUDE.md](CLAUDE.md) — модули и их правила.

## 1. История решения

> **Коротко.** Пятая итерация. Каждая следующая убирала лишнее: общую базу GL и плеера, поток движков наружу, стратегии замены и починку внутри сторожа.

| Итерация | Как было | Что не понравилось |
|---|---|---|
| 1. `core:guard` | общий `StallGuard` для GL и плеера, класс `Swap` в `GLWallpaperEngine` | подмена жила в потребителе, GL и плеер насильно сведены к одной базе |
| 2. `engine: StateFlow<PlayerEngine?>` | потребитель подключает каждый новый движок к своему GL-слоту | плеер не похож на плеер, `PlaybackMemory` шла через фабрику |
| 3. pre-roll | `PrerollSwitcher` / `SequentialSwitcher` создают движок в момент замены, сторож сам делает flush и seek | новый плеер создаётся прямо во время замены; слишком много делегатов |
| 4. фоновый запасной | два движка, новый запасной готовится в фоне по бюджету, сломавшийся запасной заменяется сразу | лишняя фоновая работа: корутина подготовки и слежка за запасным |
| 5. **Сейчас** | оба движка создаются при старте и пересоздаются только при переключении; сторож только сообщает, супервайзер решает | — |

## 2. Общая картина

> **Коротко.** Потребитель говорит плееру «рисуй сюда» и «играй/стоп» и слушает `state`. Внутри плеера один супервайзер с двумя движками, сторожем и бюджетом.

```
┌─────────────────────────── core:player ───────────────────────────┐
│  WallperPlayer (фасад, поток "WallperPlayer")                      │
│    setVideoSurface(Surface?)  play()  pause()  release()           │
│    state: Idle / Playing / Recovering / Failed                     │
│        │                                                           │
│        ▼                                                           │
│  EngineSupervisor                                                  │
│    active  ── на поверхности, играет      ┐                        │
│    standby ── prepared, на паузе, без     ├─ ExoEngineFactory      │
│               поверхности                 ┘   → ExoPlayerEngine    │
│    StallWatchdog  «встало, причина такая-то»                       │
│    RetryPolicy    сколько ещё движков можно создать и когда        │
└───────────────────────────────▲────────────────────────────────────┘
                                │ setVideoSurface / play / pause, state
┌───────────────────────── core:engine:impl ─────────────────────────┐
│  GLWallpaperEngine:    поверхность текстуры → setVideoSurface      │
│  VideoWallpaperEngine: поверхность обоев    → setVideoSurface      │
│  state = Failed  или  GL не чинится → сервис показывает заглушку   │
└───────────────────────────────┬────────────────────────────────────┘
                                │ onVideoSurfaceCreated, ремонт EGL, пульс
┌──────────────────────────── core:gl ───────────────────────────────┐
│  WallpaperGLThread + VideoWallpaperRenderer + RenderGuard          │
└────────────────────────────────────────────────────────────────────┘
```

## 3. Контракты

> **Коротко.** Наружу видны фасад, его состояние, описание медиа и фабрика. Всё остальное `internal`.

```kotlin
interface WallperPlayer {
    val state: StateFlow<WallperPlayerState>
    /** Куда рисовать; null — отключить. Ждёт, пока декодер отпустит прежнюю поверхность (≤ ~2 с). */
    fun setVideoSurface(surface: Surface?)
    fun play()
    fun pause()
    fun release()   // блокирует не дольше секунды
}

sealed interface WallperPlayerState {
    data object Idle                               // на паузе или ещё не запущен
    data object Playing
    data class Recovering(val cause: StallCause)   // активный встал, переключаемся на запасной
    data class Failed(val cause: FailureCause)     // показывай заглушку
}

class WallperPlayerFactory @Inject constructor(@ApplicationContext context: Context) {
    fun create(media: PlayerMedia): WallperPlayer
}
```

- **Нет `prepare` и `stop`.** Плеер готовится сам на первом `play()`. После 15 с паузы он освобождает оба движка, а следующий `play()` стартует с той же позиции.
- **`setVideoSurface` синхронный, как у ExoPlayer.** Когда вызов вернулся, прежнюю поверхность можно освобождать. Так делает GL при перезапуске и прямой путь в `onSurfaceDestroyed`.

Внутренняя сторона (`engine/`, без изменений, кроме `seekTo`):

```kotlin
internal interface ManagedEngine {
    val isReady: StateFlow<Boolean>      // STATE_READY, в том числе без поверхности
    val error: StateFlow<Int?>           // код PlaybackException
    val frameRate: StateFlow<Float>
    val loopBoundaries: SharedFlow<Unit>
    val positionMs: Long
    fun setSurface(surface: Surface?)
    fun snapshot(): EngineSnapshot
    fun play(); fun pause(); fun seekTo(positionMs: Long); fun release()
}

internal fun interface EngineFactory {
    fun create(positionMs: Long, surface: Surface?, playWhenReady: Boolean): ManagedEngine
}
```

## 4. Два движка

> **Коротко.** Оба движка создаются в начале `run()`. Переключение — освободить зависший, дать запасному поверхность, seek, play, и тут же создать новый запасной на место зависшего. В остальное время движки не трогаются.

### 4.1. Главный цикл

```kotlin
suspend fun run(playWhenReady: Flow<Boolean>) {
    createEngines()                                   // активный + запасной, сразу
    playWhenReady.distinctUntilChanged().collectLatest { if (it) play() else pause() }
}

private suspend fun play() {
    var engine = active ?: createEngines()            // после долгой паузы
    engine.play()
    while (true) {
        val cause = watchdog.watch(engine)            // спит, пока всё хорошо
        if (cause is Failed && cause.errorCode in CONTENT_ERROR_CODES) return fail(ContentBroken)
        val next = awaitStandby(cause) ?: return fail(RetriesExhausted(cause))
        engine = switchTo(next, from = engine, positionMs = if (cause == StuckAtClipEnd) 0 else engine.positionMs)
    }
}

private suspend fun awaitStandby(cause: StallCause): ManagedEngine? {
    while (true) {
        val delayMs = retryPolicy.acquire() ?: return null
        state = Recovering(cause); delay(delayMs)
        if (awaitReady(standby)) return standby       // ≤ 2 с; ошибка важнее готовности
        standby.release(); createStandby()            // сломался, пока ждал: новый, попытка потрачена
    }
}

private fun switchTo(next: ManagedEngine, from: ManagedEngine, positionMs: Long): ManagedEngine {
    from.release()                                    // у поверхности может быть только один продюсер
    next.setSurface(surface); next.seekTo(positionMs); next.play()
    createStandby()                                   // замена зависшему
    return next
}
```

### 4.2. Почему создание в `run()`, а не в `init`

ExoPlayer нужно вызывать только из потока его looper'а (в Media3 1.8.0 `throwsWhenUsingWrongThread = true`, иначе `IllegalStateException`). А супервайзер конструируется в `DefaultWallperPlayer` на потоке вызывающего, обычно main. Поэтому оба движка создаются первым делом в `run()`: это первое, что выполняется на потоке плеера сразу после создания `WallperPlayer`.

### 4.3. Жизнь запасного движка

- **Создаётся** с позиции 0, без поверхности и с `playWhenReady = false`: при старте, при переключении и после долгой паузы.
- **Пока ждёт, за ним никто не следит.** Если он сломался (например, кодек отобрали, 4006), это выяснится при следующем переключении: `awaitReady` сразу вернёт `false`, запасной пересоздаётся, и это стоит одну попытку бюджета.
- **Если активный встал, пока запасной ещё готовится** (например, сразу после переключения), супервайзер ждёт его до 2 с. Последний кадр всё это время на экране.
- **Долгая пауза (> 15 с)** освобождает оба движка, а `play()` создаёт их заново с запомненной позиции. Это не «проактивное пересоздание», а освобождение двух аппаратных декодеров, пока обоев не видно (см. 4.5).

### 4.4. Почему это работает без поверхности

Media3 1.8.0 без поверхности конфигурирует кодек на `PlaceholderSurface` (API 23+) или на detached surface (API 35+). Рендерер считает себя готовым по `frameReadyWithoutSurface`. Поэтому `setSurface` у готового запасного — это `MediaCodec.setOutputSurface`, кодек не пересоздаётся.

### 4.5. Цена

- **Второй декодер всё время, пока обои видны.** Запасной держит экземпляр кодека и его буферы (несколько МБ для 1080p, десятки для 4K). На паузе он ничего не декодирует. У `PlaceholderSurface` есть свой маленький поток с EGL-контекстом.
- **Поэтому на долгой паузе оба освобождаются.** Обоев не видно большую часть дня. Два удержанных аппаратных декодера — это память, риск LMK для процесса обоев и отобранные кодеки (4006), когда их просит камера.
- **Видимая заминка** при переключении: освобождение зависшего движка (обычно десятки мс, максимум таймаут release ExoPlayer, 500 мс), плюс seek и первый кадр запасного. На повторных сбоях к этому добавляется задержка бюджета (1, 3, 5 с). Кадр старого движка всё это время остаётся на поверхности.
- **Позиция.** Супервайзер берёт `positionMs` зависшего движка. Звук выключен, поэтому часы ExoPlayer могут уйти вперёд замёрзшего кадра на время обнаружения (до ~1 с).

## 5. Сторож

> **Коротко.** `StallWatchdog.watch(engine): StallCause` спит, пока декодер выдаёт кадры, и возвращает причину, когда перестал. Он ничего не чинит и ничего не помнит.

| Причина | Когда |
|---|---|
| `DecoderStalled` | READY, а кадров нет дольше 5 интервалов кадра (400–1000 мс) |
| `StuckBuffering` | буферизация дольше 1,5 с |
| `NoFirstFrame` | ни одного кадра 2 с после старта или `play()` |
| `StuckAtClipEnd` | стоит у конца клипа, переход на новый круг не случился |
| `Failed(code)` | ошибка ExoPlayer, сразу |

После перехода на новый круг даётся ещё 1 с: декодеру нужно время, чтобы снова дойти до начала клипа. Тик — 250 мс.

**Решение принимает супервайзер:**
- `Failed(2005/2008/3001/3003/4004/4005)` — файл не играет на этом устройстве, `Failed(ContentBroken)` сразу;
- всё остальное — переключиться на запасной, а если его нет — `Failed(RetriesExhausted)`.

## 6. Бюджет

> **Коротко.** `RetryPolicy` ограничивает переключения после сбоев: 4 подряд, с задержками 0, 1, 3 и 5 с перед переключением. Если с последней выданной попытки прошло 30 с, счёт начинается заново.

- **Попытку тратит** каждое переключение и каждый пересозданный сломанный запасной.
- **Первое переключение мгновенное** (задержка 0). Задержки на следующих дают системе время, если сбои идут подряд (нехватка декодеров, перегрев).
- **Создание движков при старте и после долгой паузы бюджет не тратит.** Это не восстановление: иначе частые включения экрана съели бы бюджет.
- **Итого в худшем случае** (файл не играет на устройстве, а ошибки нет): первая пара движков, 4 переключения (6 движков), потом заглушка до выбора других обоев.

## 7. GL

> **Коротко.** У рендерера одна видео-текстура на EGL-контекст, её поверхность уходит в `player.setVideoSurface`. Потеря контекста и перезапуск GL-потока плеер не трогают: он получает новую поверхность и продолжает играть.

- **`VideoWallpaperRenderer`** создаёт текстуру в `onSurfaceCreated` и сообщает `Listener.onVideoSurfaceCreated(surface)`. На каждом кадре `latch()` перевзводит `SurfaceTexture`, если колбэки кадров остановились.
- **Потеря контекста:** старая текстура уходит в `retired` без освобождения, ведь декодер ещё может в неё писать. Новая текстура отдаётся плееру. `retired` освобождается на первом кадре новой текстуры.
- **`RenderGuard`** в GL-потоке: нет кадров → перерисовать; `BAD_SURFACE` → новая EGL-поверхность, затем новый контекст; `CONTEXT_LOST` или исключение → новый контекст.
- **Перезапуск GL-потока** (GL не чинится или пульс молчит 2 с):
  1. `player.setVideoSurface(null)` и ожидание, пока декодер отпустит текстуру;
  2. остановить старый GL-поток;
  3. новый GL-поток отдаёт свою текстуру в `setVideoSurface`.

  Лимит `GlRestartPolicy`: 3 перезапуска за 2 минуты, потом заглушка.
- **Сбой GL не тратит бюджет плеера.**

## 8. Прямой путь

> **Коротко.** `VideoWallpaperEngine` отдаёт плееру поверхность обоев и отключает её в `onSurfaceDestroyed`: система забирает поверхность сразу после этого колбэка.

```kotlin
init {
    scope.launch { player.state.first { it is Failed }; host.showPlaceholder() }
    player.setVideoSurface(surfaceHolder().surface)
    player.play()
}
override fun onSurfaceDestroyed() = player.setVideoSurface(null)
```

## 9. Сценарии

| Что случилось | Плеер | Экран |
|---|---|---|
| Декодер встал / буферизация / нет первого кадра | переключение на запасной, вместо зависшего — новый запасной | последний кадр, потом видео дальше |
| Застрял у конца клипа | переключение на запасной с позиции 0 | новый круг |
| Ошибка кодека (4001, 4003, 4006…) | переключение на запасной | то же |
| Файл битый (2005, 4005…) | `Failed` сразу | заглушка |
| Встал, а запасной ещё готовится | ждёт запасного до 2 с | последний кадр дольше |
| Запасной сломался, пока ждал | ничего, пока не понадобится; при переключении пересоздаётся (попытка бюджета) | последний кадр дольше на задержку бюджета |
| Бюджет кончился, снова встал | `Failed` | заглушка |
| Пауза < 15 с | активный на паузе, запасной ждёт | — |
| Пауза > 15 с | оба движка освобождены, позиция запомнена | — |
| Снова `play()` | новая пара: активный с позиции + запасной | — |
| Потерян EGL-контекст | получает новую поверхность | новая текстура |
| GL повис или не чинится | `setVideoSurface(null)`, потом новая поверхность | новый GL-поток, лимит 3 за 2 мин |

## 10. Потоки

> **Коротко.** У плеера свой поток, у GL свой, у `GLWallpaperEngine` лёгкий поток колбэков.

- **Поток `WallperPlayer`** (`HandlerThread`): корутины супервайзера и все ExoPlayer (`setLooper`).
  - `play`/`pause` только меняют `StateFlow`.
  - `setVideoSurface` и `release` выполняются на потоке плеера, вызывающий ждёт (не дольше 2,5 с и 1 с).
- **GL-поток:** очередь задач, ожидание с тайм-аутом, пульс, ремонт EGL.
- **`WallpaperFrames`** (в `GLWallpaperEngine`): колбэки кадров, `onVideoSurfaceCreated`, пульс и перезапуск GL.

## 11. Тесты

> **Коротко.** Супервайзер, сторож и бюджет тестируются в JVM на виртуальном времени корутин и фейковых движках.

- **`StallWatchdogTest`** (7): каждая причина и её порог, запас после перехода на новый круг, ошибка сразу, сторож ничего не трогает.
- **`RetryPolicyTest`** (2): задержки и сброс через 30 с.
- **`EngineSupervisorTest`** (11):
  - оба движка созданы сразу, ещё до `play`; `play` запускает только активный;
  - зависание: порядок «старый release → запасной setSurface → seekTo → play», затем новый запасной;
  - конец клипа → seekTo 0;
  - зависание во время подготовки запасного → ждёт его;
  - запасной сломался, пока ждал → не трогается до переключения, тогда пересоздаётся;
  - битый файл → `Failed` сразу;
  - файл не играет → `Failed(RetriesExhausted)` после 6 движков;
  - долгая пауза → оба освобождены, `play` → новая пара с той же позиции;
  - короткая пауза → только pause/play;
  - новая поверхность → активному и тому, на кого переключимся.
- **`RenderGuardTest`** (7), **`UVCoordsTest`** (3) в `core:gl`.

## 12. Статус и открытые вопросы (2026-10-22)

> **Коротко.** Реализовано. Сборка debug и release зелёная, 54 unit-теста проходят: 20 в `core:player`, 10 в `core:gl`, остальные в фичах и `:app`. **На устройстве не проверено, ничего не закоммичено.**

**Где что лежит**
- `core:player`: `WallperPlayer`, `DefaultWallperPlayer`, `supervisor/` (`EngineSupervisor`, `StallWatchdog`, `RetryPolicy`), `engine/` (`ManagedEngine`, `ExoPlayerEngine`, `ExoEngineFactory`).
- `core:gl`: `VideoWallpaperRenderer` с одной текстурой, `guard/RenderGuard`, `guard/GlRestartPolicy`.
- `core:engine:impl`: `GLWallpaperEngine`, `VideoWallpaperEngine`.

**Открытые вопросы**
- **Устройство, где второй декодер не поднимается** (например, 4K на слабом SoC). Запасной всегда сломан, поэтому при зависании бюджет уходит на его пересоздание, а потом заглушка. Вариант на будущее: в этом случае пересоздавать активный движок.
- **Seek при переключении.** Для длинного GOP он может занять сотни миллисекунд. Альтернатива — переключаться на запасной с начала клипа без seek: быстрее, но видео прыгнет.

**Что проверить на устройстве**
- Зависание: в логе `WallperPlayer` строка `Switched from engine #N to #M`, на экране нет чёрного кадра.
- Экран выключен дольше 15 с и снова включён: видео продолжается с той же позиции.
- Пересоздание GL: видео продолжается без перезапуска плеера.
